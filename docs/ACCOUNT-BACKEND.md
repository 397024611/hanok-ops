# Account management backend candidate

This is an undeployed candidate for Report Boss. It does not provision users, change production grants, deploy functions, or migrate a deployed project. Do not treat isolated tests as production isolation approval.

## HTTP interface

`POST /functions/v1/ops-admin-accounts` accepts JSON with a Supabase user bearer token. The handler verifies the token with Auth and loads the caller's current `ops_profiles.role` and `active`. Only an active `admin` can continue. Every privileged database RPC independently rechecks that verified actor. `hq`, `store`, `partner`, `pending`, missing, and inactive profiles cannot manage accounts. A body-supplied actor ID is ignored.

Allowed browser origins are exactly `https://hanokops.local` and `https://baogaolaoban-report.vercel.app`; there is no wildcard. Native requests without an Origin header still require the same bearer authentication. Responses use `Cache-Control: no-store`. Function gateway JWT verification must remain enabled when this function is eventually deployed.

Actions:

- `list`: `{action:"list"}` → `{accounts, stores, pending_requests}`.
- `create`: `{action:"create", requestId, email, displayName, role:"store"|"partner", storeIds, password}` → `{ok:true, account, password_unchanged}`.
- `assign`: `{action:"assign", userId, storeIds}` → `{ok:true, account}`.
- `deactivate`: `{action:"deactivate", userId}` → `{ok:true, account}`.

An account contains `user_id`, `email`, `display_name`, `role`, `active`, `store_ids`, `created_at`, and `is_legacy_shared`. Stores contain `id`, `code`, `name`, and `active`. Account listing includes operational roles only; unrelated `pending` profiles from the shared Auth system are omitted.

A pending request contains only `request_id`, `email`, `display_name`, `role`, `store_ids`, and `created_at`, scoped to the calling admin's unfinished requests. It has no password or password hash. Another admin cannot list or adopt it. The UI can reopen the request and ask the human to reenter the initial password.

Validation: initial password at least 12 Unicode code points and at most 72 UTF-8 bytes; normalized email at most 254 characters; trimmed display name 1–100 characters; UUID request/user/store IDs; unique nonempty store list (maximum 100); staff (`store`) exactly one active store; partners one or more active stores. No creation of `hq` or `admin` roles, no cost approvals, no reset action, no reactivation action. Assignment and deactivation cannot target the caller, HQ, admin, or pending profiles. Assigning an inactive account is rejected. Shared logins cannot be reassigned.

Errors have a stable `error` code and optional `retryable:true`; provider/database error text is never echoed. Examples include `admin_required` (403), `invalid_stores` (400), `email_exists`/`request_conflict` (409), and `database_unavailable`/`account_creation_incomplete` (503). Preserve the request's values and ID on an uncertain creation result.

## Creation and recovery

1. A service-role-only RPC reserves the normalized email, immutable request fields, actor, and request ID in a private ledger. It serializes reservations for the same address and rejects preexisting/unrelated Auth users.
2. Auth creates the user with the human-entered initial password. The server sets only an immutable request marker in `app_metadata`; authorization never uses `user_metadata` or JWT role metadata. The Auth trigger creates an inactive `pending` operational profile.
3. The finalize RPC locks the request/profile, verifies the Auth email and server-controlled marker, checks active stores, writes memberships and compatible `store_id`, and activates the profile in one database transaction.
4. If Auth or the final response is lost, repeating the same request finds the marked user and resumes without resetting any password. Completed retries return current account state, including `active:false` after a later deactivation; they never reenable it.
5. A new request ID can recover an unfinished request only for the same admin, normalized email, display name, role, and exact store set. The backend uses the canonical original ID. A completed or unrelated user is never adopted by this fallback.

If Auth already created the user, the original successfully set password remains unchanged on recovery even if the human reenters a different value. The response sets `password_unchanged:true` so the UI can make that explicit. No first-login password expiry or forced password change is implemented. Abandoned unfinished requests remain discoverable; there is deliberately no user deletion or password-reset side effect.

## Database access model

The new migration is `20261008105007_account_memberships_and_active_access.sql`, generated by `supabase migration new` using CLI 2.120.0. It executes in one transaction against the existing baseline schema.

- `ops_profiles.active` defaults true for existing profiles, preserving current HQ and five shared store logins.
- Existing `store` profile `store_id` values are backfilled into `ops_store_memberships`. Memberships become the access source. New `store` profiles retain one matching `store_id` for compatibility; `partner.store_id` is null.
- `is_legacy_shared` marks only the five preexisting matching code/email/store-role bindings. It cannot be set by authenticated clients.
- Live database helpers require an active non-pending profile. Staff/partners need a membership for the ticket's store; HQ/admin retain group-wide operations.
- PUBLIC/anonymous table and column privileges on operations tables are revoked, with explicit anonymous-deny policies that remain safe even if an old grant returns. A bucket-specific anonymous storage guard leaves unrelated anonymous buckets usable.
- Restrictive policies intersect legacy permissive policies on stores, profiles, tickets, comments, attachments, events, reopen requests, notifications, push subscriptions, and the operations storage bucket.
- Staff can submit only a new ticket without assignment, due/workflow, acceptance or completion fields. Partners cannot submit tickets or change ticket status. Both may comment and attach files on assigned-store tickets. Comments must identify the caller; attachment paths must belong to their ticket.
- Staff reopen requests must be `pending` with no forged reviewer/time. The existing HQ/admin review RPC is updated to reject inactive or missing profiles, including the previous SQL NULL-role bypass.
- Own storage uploads retain INSERT + SELECT + UPDATE for interrupted `x-upsert` retries. Staff/partners cannot overwrite another user's files. Existing attachment reads and HQ/admin updates remain available. Restrictive storage guards leave unrelated buckets' preexisting policies unchanged.
- Unsupported ticket deletion, event writes, comment/attachment/reopen edits and deletions, and notification creation/deletion have restrictive PUBLIC-deny policies. Database triggers and the privileged review RPC still work. Only HQ/admin may delete operations storage objects. Notification update grants are narrowed to `read_at`, including previously broad PUBLIC/column grants.
- Deactivation sets `active=false` and removes push subscriptions without deleting Auth identities or operational history. Existing JWTs cannot make new operational reads/writes. The user's own profile remains readable so clients can show the disabled state. Already-downloaded data cannot be recalled.
- Notification/reminder generators skip inactive HQ/admin profiles. Authenticated notification reads/updates require active access to the referenced ticket.
- Management RPCs are callable only by `service_role`; authenticated users receive no membership or profile writes, including self display-name writes. Restrictive profile mutation policies reject even a surviving inherited/PUBLIC grant; PUBLIC/anon/authenticated mutation grants are also explicitly revoked. Private functions use an empty search path, and their PUBLIC execution is revoked. No service key is added to clients.

## Legacy shared-login reset route

`ops-admin-store-user/index.ts` starts from the separately verified deployed v2 source. Its exact `https://baogaolaoban-report.vercel.app` CORS origin is retained. It now requires a live active admin, a marked active shared profile matching the requested original store, and a matching Auth email. It resets only that existing shared user's password. It does not create users, upsert profiles, change role/store, repurpose personal accounts, or reactivate disabled accounts. The legacy route's existing 8-character minimum is retained, with the same 72-byte provider maximum, for this separate compatibility route; new personal accounts require 12 characters.

The SQL suite executes actual PostgreSQL semantics: the unchanged baseline migration (only the unavailable cron extension/scheduler is stubbed), the full new migration, actual database roles/grants/RLS, Auth-trigger profile provisioning, and service-only management RPCs. Fixtures are isolated in memory and contain fabricated users/data. HTTP tests run the exact new handler with mocked Auth/Data API clients; legacy runtime tests execute its TypeScript-stripped handler. These are not a live Supabase Auth/Storage integration test.

## Required before any deployment

1. Obtain a fresh authorized read-only inventory of the actual target project's public tables, grants, policies, views, Auth triggers, storage buckets, and all service-role endpoints. Project-wide authorization and cross-application isolation must be verified before release. Merely giving a new Supabase Auth user no ops memberships does not prove they cannot access unrelated permissive policies or SECURITY DEFINER APIs.
2. Compare the actual target schema with the baseline and migration assumptions. The baseline file's historical project comment is not a deployment target; no CLI project link was created here.
3. Run Supabase advisors and a real isolated Supabase integration test including Auth, Storage owner assignment/upsert, existing JWTs, and both Edge functions. PGlite substitutes only for PostgreSQL tests; real Auth, Storage, Edge, and advisor checks remain distinct requirements.
4. Audit out-of-repository service-role endpoints (including AI/notification/push jobs) for live `active` checks and appropriate scope. Service-role access bypasses RLS. Removing subscriptions and tightening database policies cannot recall already-sent push notifications or data cached by an external service.
5. Verify any previously issued signed storage URLs and their lifetimes. Current portal/HQ source uses authenticated downloads, but externally issued signed URLs may remain valid until expiry.
6. Only after explicit deployment authorization, back up and deploy the migration, new function, and hardened legacy function together, preserving gateway JWT verification. Smoke-test existing shared logins and HQ operations, create/assign/deactivate isolated test accounts, and confirm another-app accounts/data remain unaffected. No such production steps were performed for this candidate.
